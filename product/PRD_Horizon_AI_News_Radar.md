## 第一部分：产品定位与战略

### 1.1 产品愿景

**让每个人拥有自己的 AI 信息雷达。**

信息爆炸时代，用户每天被数千条推送淹没。Horizon 不是又一个聚合器 -- 它是一套**能思考的筛选系统**：从数十个信息源抓取原始内容，由 AI 理解语义、判断重要性、消除冗余、补充背景，最终输出一份高质量、有深度的个性化简报。用户无需在数十个 APP 间切换，无需手动筛选噪音，只需要阅读。

### 1.2 产品定位

Horizon 定位为**面向知识工作者与科技从业者的 AI 原生信息助理**，对比市场上现有产品：

| 维度 | 传统 RSS 阅读器 | 社交平台算法推荐 | Horizon |
|------|----------------|------------------|---------|
| 信息源 | 用户手动订阅 | 平台生态闭环 | 跨平台多源自动聚合 |
| 筛选机制 | 元数据规则 | 行为打标 | **AI 语义理解 + 多维度评分** |
| 去重 | 无（URL 级别） | 无 | URL 去重 + **AI 语义去重** |
| 输出形式 | 原始内容列表 | 信息流 | **结构化双语简报 + 深度背景** |
| 个性化 | 源级别 | 行为反馈 | 兴趣配置 + **话题偏好控制** |
| 开放性 | 高 | 封闭 | **全开源 + 插件式架构** |

### 1.3 核心用户画像

**用户 A：技术研究员 / 工程师**

- 每日需要跟踪 AI、开源、学术、业界动态
- 信息源分散在 Hacker News、Twitter/X、ArXiv、GitHub、微信公众号
- 痛点：信息过载严重，核心信息与噪音比例 1:10
- 需求：高信噪比、深度背景补充、技术细节保留

**用户 B：产品经理 / 行业分析师**

- 关注宏观趋势、政策动态、竞品分析、行业报告
- 信息源偏重机构报告、新闻网站、Telegram 频道
- 痛点：领域覆盖广但深度不够，数据与洞察分离
- 需求：跨领域的广度覆盖、AI 辅助的洞察提炼

**用户 C：信息焦虑的深度阅读者**

- 害怕错过重要信息（FOMO），但时间有限
- 订阅了大量的 Newsletter 和 RSS
- 痛点：Mark-all-as-read 恶性循环
- 需求：一份精心筛选的"今日必读"清单

### 1.4 竞争格局与差异化

| 产品 | 优势 | 局限 | Horizon 如何超越 |
|------|------|------|-----------------|
| Feedly / Inoreader | 成熟的 RSS 生态 | 无 AI 筛选，无跨源去重 | AI 语义评分 + 多源融合 |
| Ground News | 媒体偏见分析 | 源数量有限，无深度扩展 | 多维度评分 + AI 背景补充 |
| DailyBot / Brief | 团队协作 | 泛化，不面向个人 | 个人化 + 全栈可定制 |
| 自行搭建（n8n + 模型） | 灵活 | 维护成本高 | 开箱即用 + 容器化部署 |

## 第二部分：用户需求与场景分析

### 2.1 核心用户故事

```
作为一名工程师（用户 A），我每天早晨打开 Horizon 可以看到：
- 按重要性排序的今日技术要闻
- 每条新闻用 2-3 句话概括核心
- 对涉及的技术概念有背景解释
- 同一热点聚合了多个信源的报道
- 英文内容自动翻译为中文

作为一名分析师（用户 B），我使用 Horizon 可以：
- 追踪特定领域（如 AI 监管、芯片政策）的长线动态
- 获取机构报告的 PDF 原文和 AI 摘要
- 按主题而非时间线组织信息

作为一名深度阅读者（用户 C），我期望：
- 看到信息来自哪些源头及其可信度
- 一键阅读全文或保存到稍后读
- 根据个人兴趣调整优先级
```

### 2.2 关键场景流

**场景 1：每日晨间简报**

```
用户打开 Horizon Dashboard
  → 看到今日简报：按 AI 评分排序的 10-15 条关键信息
  → 每条包含：标题、摘要、来源信誉、社群讨论热度
  → 扩展阅读：感兴趣条目点击 "详情" 查看 AI 撰写的深度背景
  → 双语切换：英文原文 / 中文翻译一键查看
```

**场景 2：突发事件追踪**

```
某条技术新闻在 Twitter + HN + GitHub 同时出现
  → Horizon 从多个源抓取到同一事件
  → AI 语义去重识别出这些碎片属于同一件事
  → 合并所有信息源的内容，保留最完整版本
  → 标记为高优先级（多源印证提升可信度）
  → 生成带多源溯源的聚合条目
```

**场景 3：领域深度调研**

```
用户关注 AI 安全（AI Safety）领域
  → 在 Horizon 配置中将 AI Safety 设为高优先级话题
  → AI 在打标时对 AI Safety 内容给予更高权重
  → 日报中该领域内容占比提升
  → 同时收集相关的学术论文和机构报告
  → 跨周跨月的长线追踪（Roadmap 功能）
```

### 2.3 用户痛点与解决策略

| 痛点 | 根因分析 | 解决策略 | 衡量指标 |
|------|---------|---------|---------|
| 信息过载 | 缺乏语义级筛选 | AI 多维评分 + 阈值过滤 | 用户日报阅读完成率 > 70% |
| 跨源信息碎片化 | 同一事件分散在不同平台 | URL 去重 + AI 语义去重 | 重复内容占比 < 5% |
| 缺乏深度语境 | 标题党太多，正文被隐藏 | AI 自动搜索背景信息 | 用户展开深度阅读率 |
| 语言障碍 | 优质内容多为英文 | 双语输出 + AI 翻译 | 中文用户使用天数 |
| 定制不足 | 一刀切的推荐 | 用户兴趣配置 + 话题偏好 | 偏好设置使用率 > 30% |

### 3.2 模块化功能定义

#### 3.2.1 数据摄取层 -- 开放、可扩展的信息管道

**核心能力：** 对接多元信息源，统一数据模型，为上层处理提供标准化输入。

**功能列表：**

| 功能 | 优先级 | 复杂度 | 说明 |
|------|--------|--------|------|
| 通用 RSS/Atom 抓取 | P0 | 低 | 支持任意 feed 订阅，自动检测更新 |
| Hacker News 集成 | P0 | 中 | 首页 + 新帖 + Show HN + Ask HN |
| Twitter/X 集成 | P1 | 高 | Playwright 模拟登录爬取指定用户/关键词 |
| Telegram 频道集成 | P1 | 中 | 通过 Telegram API 获取频道消息 |
| GitHub Trending 集成 | P1 | 低 | 获取热门仓库与 Releases |
| Reddit 集成 | P2 | 低 | 子版块热帖与讨论 |
| 微信公众号集成 | P2 | 高 | 通过本地 RSS 服务间接获取 |
| GDELT 全球事件库 | P2 | 中 | 实时全球新闻事件流 |
| Google News 集成 | P2 | 低 | 按主题聚合的新闻流 |
| OpenBB 金融数据 | P3 | 高 | 金融新闻与市场数据 |
| 学术论文源 | P1 | 中 | OpenAlex + Hugging Face Papers |
| 机构报告源 | P1 | 中 | 阿里研究院等 PDF 报告下载 |

**设计决策背后的思考：**

- **为什么统一数据模型？** 不同源的数据结构差异巨大（推文 280 字 vs 论文 20 页）。统一为 `ContentItem` 让上层处理逻辑与源无关，新增一个源只需实现一个 `fetch()` 方法，属于典型的策略模式。
- **为什么不将社交媒体作为主力源？** 社交媒体噪声比高，但又是突发事件的第一现场。Horizon 的策略是将社交内容作为"发现层"，结合 AI 评分和权威源交叉验证后再推荐给用户。

#### 3.2.2 智能处理层 -- AI 驱动的信息理解

这是 Horizon 的核心竞争力所在，也是 AI 能力深度嵌入产品设计的集中体现。

**子模块 1：AI 评分引擎**

每条信息经过 8 维度评分后得到 0-10 的综合分：

| 维度 | 权重 | 说明 | AI 判断依据 |
|------|------|------|------------|
| 源权威性 (Source Authority) | 20% | 信息源的可靠程度 | 源类型（官方/社交/学术）× 历史准确率 |
| 新颖性 (Novelty) | 15% | 与其他已处理内容的差异度 | 与历史内容的语义对比 |
| 技术深度 (Technical Substance) | 20% | 内容的技术含量 | 术语密度 × 逻辑深度 × 论据完整性 |
| 现实影响力 (Real-world Impact) | 15% | 对现实世界的影响范围 | 涉及人数 × 经济影响 × 政策关联 |
| 社群验证 (Community Validation) | 10% | 社群讨论的活跃度与质量 | 评论数 × 点赞数 × 高赞评论质量 |
| 内容完整性 (Content Completeness) | 10% | 信息是否完整、独立可读 | 是否有背景、数据、结论等完整要素 |
| 营销惩罚 (Marketing Penalty) | -10%~0 | 是否为软文/推广 | 营销话术检测 × 商业推广信号 |
| 重复惩罚 (Duplicate Penalty) | -10%~0 | 与近期已处理内容的相似度 | 语义相似度 × 话题重复度 |

**设计思考：** 传统的单一分数无法区分"重要但不紧急"与"紧急但不重要"。多维评分让用户可以根据自己的偏好调整权重（例如：研究员可以提升技术深度权重，分析师提升影响力权重）。这也为后续的用户画像学习埋下伏笔。

**子模块 2：AI 语义去重**

```
输入：来自多个源的原始内容列表
  → Stage 1：URL 级别去重（规则引擎）
    → 规范化 URL（去除 www、尾部斜杠、跟踪参数）
    → 同 URL 合并，保留最完整版本
  → Stage 2：AI 语义去重
    → AI 判断两个内容是否报道同一事件
    → 将重复内容的来源信息合并到主条目
    → 生成 Source Provenance（跨源溯源数据）
输出：无冗余的、带溯源信息的条目集合
```

**设计思考：** 两阶段设计是有意为之。URL 去重是确定性算法（O(n) 复杂度、零成本），语义去重需要调用 AI（有成本和延迟）。先做前者去掉明显的重复，减少 AI 调用量。这是典型的"用规则解决 80% 问题，AI 解决剩余 20%"的工程思维。

**子模块 3：AI 深度解析 (Enrichment)**

当用户展开某条新闻的详情时，Horizon 展示的不仅是一篇摘要，而是一个 AI 生成的**微型专题**：

- **背景解释：** 这条新闻涉及哪些前置知识？（技术概念、历史事件、关键人物）
- **详细总结：** 发生了什么？为什么重要？各方观点是什么？
- **社群讨论：** Hacker News / Reddit 等平台的高质量评论摘编
- **关联信息：** 相关的学术论文、机构报告、历史事件

实现方式：AI 先提取需要解释的概念 → DuckDuckGo 搜索 → 阅读搜索结果 → 生成结构化内容。这个过程不需要调用昂贵的搜索 API，完全依赖公开网页检索，体现了成本意识与工程取舍。

**子模块 4：均衡摘要 (Balanced Digest)**

```
需求背景：单纯按分数排序会导致热门领域（AI）挤占其他领域（生物、物理、政策）
解决方案：按类别组设置配额上限

算法：
  1. 按类别将条目分组
  2. 每组内按分数排序
  3. 从分数最高的条目开始选取，逐轮填入各组配额
  4. 每组不超过配额上限，总条目不超过 max_items 上限
  5. 确保多样性：同一话题的最多出现次数（可选）

输入示例：
  AI: 20条 → 配额 5 → 取前 5
  生物: 3条 → 配额 5 → 取全部 3
  政策: 8条 → 配额 5 → 取前 5
  最终简报：13 条，跨 3 个领域
```

**设计思考：** 这个算法看似简单，但在实际操作中至关重要。如果只做"Top N"，用户的日报可能变成"AI 日报"而非"今日要闻日报"。配额不是上限而是保障 -- 确保每个重要领域都有被看到的机会。这是一种产品价值观的显性表达：**多样性是信息质量的重要维度**。

#### 3.2.4 扩展层 -- AI Native 的交互范式

**MCP 服务器：** Horizon 提供 MCP（Model Context Protocol）接口，允许 AI 助手直接驱动 Pipeline：

```
AI 助手 → MCP 协议 → Horizon MCP Server
  → fetch_all_sources()    // 触发数据抓取
  → score_items()          // AI 评分
  → filter_and_dedup()     // 去重与过滤
  → enrich_items()         // 深度解析
  → generate_summary()     // 生成简报
  → 返回结构化结果供 AI 使用
```

**设计思考：** MCP 是 Horizon 的一个前瞻性设计。当 AI 助手成为新的交互范式时，信息工具不应该只有人类用户界面。MCP 让 Horizon 的数据处理能力可以被任何 AI 系统调用 -- 用户可以通过自然语言与 AI 助手对话，让 AI 驱动整个信息获取-处理-呈现链路。这是一种真正的 **AI-First 架构**。

### 4.2 架构设计原则

**原则 1：模块边界清晰，可独立测试**

每个处理阶段是独立的模块，有自己的接口和数据模型。这使得：
- 可以单独测试每个阶段（`test_analyzer.py`、`test_dedup.py`）
- 可以在不需要完整 pipeline 的情况下使用某个模块（如通过 API 单独调用去重）
- 替换某个 AI 提供商不影响其他模块

**原则 2：AI 是引擎而非胶水**

AI 被用在最需要理解能力的地方（评分、去重、摘要、背景扩展），而非用 AI 来粘合模块。确定性算法（URL 规范化、配额分配、缓存策略）与 AI 策略搭配使用，各司其职。这是**系统分析能力**的体现 -- 在做架构决策时，识别出哪些问题适合用规则解决，哪些需要 AI 理解。

**原则 3：渐进式复杂度**

- 默认配置开箱即用
- 高级用户可以通过配置深度定制
- 开发者可以通过 MCP / API / CLI / Docker 进行二次开发
- 不需要 AI 能力的用户也可以使用基础的 RSS 聚合功能

### 4.3 AI 提供商抽象 -- 多模型、零锁定的设计

Horizon 的 AI 客户端设计是一个经过深思熟虑的抽象层：

```
AIClient (接口)
  ├── AnthropicClient    — Claude 原生 SDK
  ├── OpenAIClient       — OpenAI 兼容 API（也覆盖 DeepSeek、DashScope、ollama）
  ├── AzureOpenAIClient  — Azure 专属部署
  ├── GeminiClient       — Google GenAI SDK
  └── ChainedAIClient    — 多提供商故障转移链
     ├── Claude (首选)
     ├── DeepSeek (降级)
     └── Ollama (自托管，最后兜底)
```

这个设计体现了几个关键的工程决策：

1. **统一接口，屏蔽差异：** 所有客户端实现同一个 `async complete()` 方法，上层调用者无需关心底层是 Claude 还是 Ollama。

2. **ChainedAIClient 的故障转移：** 当主要 AI 提供商不可用时（限流、服务中断），自动降级到备用提供商。这对一个需要每日定时运行的 Pipeline 至关重要 -- 一个故障就导致整日报废是不可接受的。

3. **提供商标配化适配：** 同一个提示词在 Claude 和 DeepSeek 上表现不同，但 Horizon 的 Prompt 设计（`src/ai/prompts.py`）通过结构化的 JSON schema 约束输出格式，降低模型差异带来的不确定性。核心 Prompt 设计思路：**将 AI 当作函数来调用** -- 输入结构化数据，指定输出 schema，让 AI 在约束框架内"填空"而非自由发挥。

### 4.4 数据模型与存储设计

**统一数据模型 `ContentItem`：**

```
ContentItem
├── 标识：id (source_type:subtype:native_id), url, title
├── 时间：published_at, fetched_at
├── 内容：content, raw_content, clean_content, display_html
├── 来源：source_type, source_attribution, source_provenance
├── AI 评分：ai_score (0-10), score_breakdown (8 维度)
├── 分类：category, topics[], tags[]
├── 语言：original_language, is_ai_translated
├── 富内容：cover_image, images[], author, comments[]
└── 扩展：enrichment （背景、详细总结、讨论）
```

**存储策略：**

| 数据类型 | 存储方式 | 查询需求 |
|---------|---------|---------|
| 新闻条目 | SQLite 主表 + FTS5 全文索引 | 时间序、分类、搜索、话题 |
| 论文 | 独立 papers 表 | 按源/分类/年份过滤 |
| 报告 | 独立 reports 表 + PDF 文件存储 | 按机构/关键词筛选 |
| 用户偏好 | user_topic_prefs 表 | 匿名用户 ID 方案 |
| 配置 | config.json + .env 变量注入 | 热加载 |
| Pipeline 运行 | MCP RunStore 快照到磁盘 | 调试和恢复 |

**设计决策 -- 为什么选择 SQLite 而非 PostgreSQL？**

- **部署复杂度：** Horizons 的运行模式是单用户/单机 Pipeline，不需要多进程并发写入。SQLite 零运维、零依赖的特性让部署成本降到最低（`uv run horizon` 即可）。
- **性能天花板：** 对于个人使用的数据量级（每日数百条、累计数十万条），SQLite 完全胜任。如果未来需要多用户协作，API 层可以替换为 PostgreSQL 而无需修改 Pipeline 逻辑。
- **文件即数据库：** 数据库文件可以随着日报一起备份、迁移。这是产品价值取向的体现 -- 让用户真正拥有自己的数据。

### 4.5 MCP 服务器的设计思考

MCP 服务器是 Horizon 中 AI-First 架构思想的集中体现。传统的 API 是为"人类开发者调用机器"设计的，而 MCP 是"AI 调用机器"的协议。

```
传统架构：用户 → 前端 → API → 后端
AI-First 架构：用户 ↔ AI 助手 ↔ MCP → Horizon Pipeline → 数据
```

在 Horizon 的上下文中，MCP 工具让 AI 可以：

- `run_full_workflow(hours=24)` -- 一键执行完整 Pipeline
- `fetch_sources(sources=["hn", "twitter"])` -- 选择性抓取
- `score_items(items=[...])` -- 对特定内容重新评分
- `enrich_item(item_id="...")` -- 对特定条目进行深度扩展

这意味着用户可以通过自然语言与 Horizon 交互："帮我看看今天 AI 安全领域有什么值得关注的新论文？" -- AI 助手通过 MCP 调用 Horizon，从抓取到分析到呈现全部自动完成。

## 第五部分：AI 能力设计深度解析

### 5.1 AI 能力边界认知

> 作为项目负责人，我对 AI 能力的边界有清晰认知。以下是对 Horizon 中 AI 使用的"能"与"不能"的明确界定。

**AI 擅长的（Horizon 使用的）：**

| 能力 | 在 Horizon 中的应用 | 成功标准 |
|------|-------------------|---------|
| 语义理解 | 判断两条内容是否讨论同一事件 | 去重准确率 > 90% |
| 文本分类 | 将新闻归入话题分类 | 分类准确率 > 85% |
| 质量判断 | 多维评分 | 与人工评分 Spearman 相关系数 > 0.7 |
| 摘要生成 | 生成双语摘要 | 信息完整度 > 80% |
| 知识关联 | 通过搜索为新闻补充背景 | 补充内容相关性 > 80% |
| 信息提取 | 从文本中提取概念、实体、关系 | 提取准确率 > 90% |
| 翻译 | 中文 ↔ 英文 | 可读性评分 > 4/5 |

**AI 不擅长的（Horizon 规避的）：**

| 场景 | 原因 | Horizon 的处理方式 |
|------|------|------------------|
| 确定性的规则判断 | AI 输出不稳定 | 使用规则引擎（URL 规范化、日期解析） |
| 高频低延迟操作 | 成本高、延迟不稳定 | 先由规则引擎处理 80% 的明显重复 |
| 事实性核验 | AI 会幻觉 | 每次搜索结果标注来源链接 |
| 数值计算 | 不精确 | 评分中 AI 给出文本判断，项目负责人设计权重公式 |
| 用户画像 | 隐私风险 | 完全在本地处理，不上传用户数据 |

### 5.2 提示词工程（Prompt Engineering）的设计哲学

Horizon 的 AI 提示词集中管理在 `src/ai/prompts.py`，设计遵循以下原则：

**原则 1：结构化输出（Structured Output）**

```
不良示范： "请分析这条新闻的重要性。"
良好实践： "请给出以下维度的评分（每项 0-10）：
  - source_authority: 来源权威性
  - novelty: 新颖性
  - technical_substance: 技术深度
  ...
  输出 JSON 格式。"
```

结构化输出让 AI 的行为可预测、可调试、可测试。每个 Prompt 都有明确的输入 Schema 和输出 Schema，AI 在给定的框架内填充，而非自由写作。

**原则 2：示例驱动（Few-shot Learning）**

对于分类任务，Prompt 中嵌入示例比单纯描述更有效。例如话题分类时，Prompt 包含每个话题的种子关键词列表（`src/seed_topics.py`），让 AI 理解某个话题的语义范围。

**原则 3：容错设计**

AI 输出可能不符合预期格式。Prompt 设计包含：
- 明确的格式约束（"严格按照 JSON 格式输出"）
- 合理的默认值（当 AI 不确定时给出 0-10 中间值）
- 后处理校验（解析 JSON 失败时回退到默认评分）

### 5.3 AI 驱动的工作流优化

```
传统信息处理流程：
用户 → 打开 10 个 APP → 扫描标题 → 打开感兴趣的文章 → 手动翻译 → 理解背景

Horizon AI 增强流程：
用户 → 打开 Horizon → 阅读 AI 筛选的简报 → 展开感兴趣的条目 → 阅读 AI 补充的背景
                                                              → 一键阅读原文
```

这个流程将用户从"信息奴隶"转变为"信息指挥官" -- 用户不需要被动接受推送流，而是在 AI 过滤后的高质量信息池中进行主动筛选。

### 5.4 AI Token 成本控制

作为一个开源项目，成本意识是重要的设计考量：

| 策略 | 效果 | 实现方式 |
|------|------|---------|
| 批量处理 | 减少请求数，利用 Prompt Caching | analyze_batch() 一次性处理多条 |
| 规则预过滤 | 减少不必要 AI 调用 | URL 去重先过滤明显重复 |
| 可配置模型 | 用户根据预算选择 | Claude（高质量）、DeepSeek（平衡）、Ollama（免费） |
| 缓存 | 避免重复计算 | 内容哈希缓存 + SQLite 持久化 |
| 异步并发控制 | 控制速率，避免 429 | ai.throttle_sec + ai.analysis_concurrency |

### 6.2 数据分析驱动产品决策的方法论

**案例分析 -- AI 评分阈值的动态优化：**

```
当前状态：固定阈值 5.0，每日约 15% 的条目通过
假设：不同信息源的质量分布在差异，单一阈值可能不最优

分析方法：
  1. 按源类型分组计算通过率
  HN: 通过率 22% | RSS: 12% | Twitter: 8% | Papers: 35%
  2. 分析通过率低的原因
  Twitter 通过率低 → 噪声确实高 → 保持低阈值
  RSS 部分源通过率低 → 可能是订阅源匹配度不高 → 提示用户优化订阅
  3. 交叉分析通过率与用户行为
  某源通过率低但用户展开率高 → 该源质量高但 AI 打分偏低 → 调整评分权重
  某源通过率高但用户展开率为 0 → 该源内容不相关或摘要无吸引力 → 降低权重或检查摘要质量

输出建议：
  - 为不同源类型设置差异化基础权重
  - 动态阈值：基于用户上周收藏率自动微调
  - 用户仪表盘添加"通过率分析"视图
```

**数据分析的核心思路：** 不是在找答案，而是在找线索。数据告诉你哪里有异常，但为什么异常需要结合对业务和用户的理解来判断。上述分析中，同样一个"通过率低"，对不同源的分析结论完全不同，需要**系统分析能力**和**业务理解**的结合。

### 6.3 数据驱动的产品迭代

| 阶段 | 数据需求 | 决策输出 |
|------|---------|---------|
| 验证期（MVP） | Pipeline 成功率、每日条目数 | 核心流程是否跑通 |
| 增长期 | 用户留存、收藏率、搜索使用率 | 功能优先级调整 |
| 成熟期 | 话题偏好分布、时段活跃曲线 | 个性化推荐、定时推送 |

## 第九部分：附录

### 附录 A：技术选型理由

| 组件 | 选择 | 替代方案 | 选型理由 |
|------|------|---------|---------|
| 语言 | Python + TypeScript | Go/Rust | Python AI 生态最完善，TypeScript 前端最成熟 |
| 包管理 | uv | pip/poetry | 性能 10-100x 优于 pip，兼容 requirements.txt |
| 数据库 | SQLite | PostgreSQL | 零运维、文件级可移植性，个人使用场景足够 |
| AI 框架 | 自定义抽象层 | LangChain | 避免过度抽象，精细控制每个 AI 调用的上下文 |
| Web 框架 | FastAPI | Flask/Django | 异步原生，自动 OpenAPI 文档，性能强 |
| 前端框架 | React 19 + Vite | Next.js/Nuxt | SPA 足够，SSR 复杂度超出需求 |
| CSS | Tailwind v4 + CSS 变量 | styled-components | 零运行时开销，设计系统统一管理 |
| 测试框架 | pytest | unittest | 生态最丰富，fixture 机制灵活 |
| 部署 | Docker + GitHub Actions | Kubernetes | 单服务 + 定时任务，K8s 过度设计 |

### 附录 B：安全与隐私

- **API 密钥管理**：所有密钥通过 `.env` 注入，`config.json` 只存环境变量名引用
- **无用户数据上传**：所有处理在本地完成，不依赖外部身份服务
- **匿名用户系统**：浏览器生成随机 UUID 作为身份标识，不收集个人信息
- **依赖安全**：定期通过 `uv audit` 检查依赖漏洞
- **配置暴露风险**：API server 有 `HORIZON_API_ENV` 守卫保护调试接口

### 附录 C：已知局限与未来改进方向

- **社交媒体抓取依赖模拟登录**：Twitter/X 和微信公众号的抓取不够稳定，长期需要官方 API 或替代方案
- **单用户架构**：不支持多用户隔离，多租户需引入用户系统
- **AI 幻觉风险**：AI 补充的背景信息可能包含不准确内容，当前通过标注来源提示用户
- **PDF 报告处理**：中文 PDF 的 OCR 识别准确率有提升空间
- **定时 Pipeline 依赖 GitHub Actions**：个人部署场景需要本地 cron 方案

## 关于这份产品文档

这份产品文档不仅是对 Horizon 产品的描述，更是对我作为项目负责人能力的综合展示：

- **系统分析能力**体现在架构设计的每个决策背后 -- 从两阶段去重算法到均衡摘要的配额策略，从 ChainedAIClient 的故障转移到 SQLite 的选型理由。每个选择不是凭空发生的，而是经过"问题识别 → 方案对比 → 取舍权衡 → 验证确认"的完整分析链路。

- **AI 能力认知**体现在 AI 在 Horizon 中的定位 -- 不是作为一个噱头或包装，而是深入到 Pipeline 的每个决策节点。我清楚 AI 的边界在哪里：让它做语义理解而非数值计算，做分类排序而非事实核验，做摘要生成而非用户画像。

- **用户洞察力**体现在对三类用户的细分、对痛点的量化分析、以及每个产品功能与用户需求的显式关联。功能不是为存在而存在，每个模块都能回溯到具体的用户故事。

- **产品热情**体现在对细节的关注 -- 双语一键切换、多源溯源图表、均衡摘要算法保障信息多样性、统一的磨砂玻璃设计语言。这些功能不是核心链路必需的，但它们决定了产品是"能用"还是"好用"。

- **数据分析能力**体现在完整的指标体系设计和具体的分析案例。从采集方式到目标值到分析用途，数据不是事后统计，而是产品决策的前置驱动力。

- **团队协作能力**体现在代码管理规范、质量保障体系、沟通协作机制的制度化。一个产品做得再好，如果团队不可持续、代码不可维护，最终也会崩盘。
