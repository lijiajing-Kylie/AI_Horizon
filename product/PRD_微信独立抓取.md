## 一、背景与问题

### 1.1 现状

Horizon 的微信公众号内容目前是这样进来的：

- **新闻管道**（`horizon`）每天跑一次（GitHub Actions 定时，固定北京时间 08:17），运行到"抓取微信"这一步时，一次性把 31 个订阅公众号全部拉一遍文章列表 + 逐篇抓全文。
- **报告管道**（`horizon-reports`）独立运行时，又把其中 2 个公众号（腾讯研究院、阿里研究院）的文章再抓一遍，走报告的处理流程。

两条管道各自调微信抓取通道（`src/we_read/`），抓完即用、不落中间层。

### 1.2 三个问题

**问题一：风控风险（核心痛点）。** 所有公众号在固定时刻被集中抓取——这是微信转发服务和微信风控最容易识别的行为模式。一旦被限流或封禁，当天的微信内容就全部拿不到，且没有任何事后补救手段。

**问题二：重复抓取。** 同一批公众号（如腾讯研究院）既在新闻订阅里、又在报告源的账号列表里，每天被两条管道各抓一遍，既浪费转发服务的请求配额，又放大风控暴露面。

**问题三：不透明、不可补。** 抓取、分析、过滤全部挤在一次运行里。抓取失败直接反映为当天日报缺微信内容，用户无从知道是"没有内容"还是"没抓到"，也无法事后单独补抓。

### 1.3 方案要解决什么

把"抓取"和"分析/过滤"解耦：微信抓取由**独立常驻任务**全天分散执行（每个公众号随机间隔 4-8 小时），抓到的文章先落一张**中间表**；日报和报告运行时只从中间表读数据，再走各自原有的分析、过滤流程。一次抓取，两处消费，互不干扰。

## 二、目标与非目标

### 2.1 目标

1. **降低风控暴露**：把"固定时刻集中抓取"改成"全天分散、每号随机时间点抓取"。
2. **消除重复抓取**：同一篇文章只被抓一次，新闻和报告管道共享同一份原始数据。
3. **解耦抓取与分析**：抓取失败不影响对已有内容的分析；分析失败不影响已抓内容的存储。
4. **事后可补**：抓取任务可单独补跑（`once` 模式），日报/报告可随时重跑消费已有数据。
5. **可迁移部署**：打包发给别人，对方换台机器、装好依赖、扫码登录后一条命令即可开始采集，不依赖 crontab / systemd / GitHub Actions 等外部调度。

### 2.2 非目标（本期不做）

- 不做多用户隔离、不做前端改动、不改查询 API。
- 不迁移历史微信数据到中间表（中间表从功能上线起开始累积）。
- 不改变内容范围与评分口径：微信文章进日报后仍走原有 AI 打分、过滤、回填逻辑；进报告库后仍走原有的 AI 相关度评估。
- 不替代微信登录机制：登录仍需用户用 `horizon-wxmp login` 扫码完成（微信账号凭证不能打包分发）。

## 三、用户场景

### 场景 1：个人每天收日报

用户 A 在自己的机器（或一台小 VPS）上跑着微信抓取常驻进程。进程全天按各公众号的随机时间点采集文章到中间表。每天早上定时跑 `horizon` 生成日报时，微信文章直接从中间表取出、参与打分和筛选，与从前看到的内容质量一致，但抓取行为不再集中在同一时刻。

### 场景 2：换机器部署

用户 B 把源码打包发给朋友。朋友安装依赖、拷贝配置文件、扫码登录微信后，运行 `horizon-wxmp-collector` 一条命令即可开始采集；再跑 `horizon` / `horizon-reports` 生成内容。无需配置任何系统级定时器。

### 场景 3：报告管道取微信报告

报告管道运行 `horizon-reports` 时，从中间表里筛出报告类公众号（腾讯研究院、阿里研究院）最近的文章走报告流程（AI 相关度评估、正文清洗、PDF 解析）。这些文章不需要报告管道再去网络抓一遍。

### 场景 4：抓取任务挂了 / 还没跑起来

新机器上采集进程还没来得及跑（中间表为空），此时直接跑 `horizon` 生成日报——微信部分自动降级为"临时实时抓一次"，保证日报不丢微信内容，而不是空手而归。

## 四、需求明细

### 4.1 独立抓取任务（Collector）

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F1 | 提供一个常驻进程命令（`horizon-wxmp-collector`），一条命令启动后持续运行 | P0 |
| F2 | 每个公众号独立调度：在 4-8 小时区间内随机一个间隔，到点只抓该号；各号互不牵制、时间随机错开 | P0 |
| F3 | 首次启动时各号随机初始化首次计划时间，避免启动瞬间全部开抓 | P0 |
| F4 | 单篇正文抓取失败时保留文章、正文留空，不拖垮整个公众号 | P0 |
| F5 | 单号整体失败（网络/限流/登录失效）时跳过该号、记录日志，进程继续跑其他号 | P0 |
| F6 | 支持 `once` 子命令：抓一轮全部公众号后退出（用于手动补抓 / CI 一次性补数据） | P1 |
| F7 | 支持 `status` 子命令：查看每号上次同步时间、下次计划时间、中间表计数 | P1 |
| F8 | 支持 `reset-news` 子命令：清掉某天的新闻消费标记（用于崩溃后重跑恢复） | P1 |
| F9 | 进程可优雅停止（Ctrl+C / kill 信号），不产生半写状态 | P2 |

### 4.2 中间表存储

| 编号 | 需求 | 优先级 |
|------|------|--------|
| S1 | 新增 `wxmp_articles` 表，跨日期累积存微信文章；文章 URL 唯一，重复抓取幂等覆盖、不产生重复行 | P0 |
| S2 | 每篇存：公众号、标题、URL、发布时间、正文 HTML、清洗后 HTML、纯文本、抓取时间 | P0 |
| S3 | 带新闻消费标记（按日报 run_date）与报告消费标记（按时间戳），两条管道各自记账、互不影响 | P0 |
| S4 | 表与现有 `items` / `reports` 表无 schema 耦合；删除该表不影响其它表 | P0 |
| S5 | 数据保留与自动清理：默认只清理"已被两条管道消费且发布超 60 天"的行，未消费数据不删；清理保留期可配置 | P1 |

### 4.3 新闻管道消费（日报）

| 编号 | 需求 | 优先级 |
|------|------|--------|
| N1 | `horizon` 运行时，微信来源改为从中间表读窗口内文章，走原有打分/过滤/日报流程，流程本身零改动 | P0 |
| N2 | 同一篇文章在同一 run_date 内只处理一次（消费标记生效） | P0 |
| N3 | 中间表为空（新机器/采集未跑）时自动降级为实时抓取，日报不丢微信内容 | P0 |
| N4 | 提供开关（`use_collector`）与 `--live-wxmp` 参数，可随时切回旧的实时抓取行为 | P0 |

### 4.4 报告管道消费（报告库）

| 编号 | 需求 | 优先级 |
|------|------|--------|
| R1 | `horizon-reports` 运行时，微信报告源改为从中间表读账号对应文章，走原有评估/清洗/PDF 流程 | P0 |
| R2 | 中间表无数据时降级为实时抓取 | P0 |
| R3 | 提供开关（`use_store`）切回旧行为 | P0 |

### 4.5 可迁移性

| 编号 | 需求 | 优先级 |
|------|------|--------|
| M1 | 新机器最小步骤：装依赖 → 拷配置 → 扫码登录 → 一条命令启动采集，不配 crontab/systemd | P0 |
| M2 | 依赖外部的物仅两项：微信转发服务（默认公共地址，可配置）与微信登录态（用户扫码） | P0 |

### 4.6 可回滚性

| 编号 | 需求 | 优先级 |
|------|------|--------|
| X1 | 实测效果不好时，删除采集包 + 关闭开关即可完全回到旧的实时抓取行为，现有数据不受损 | P0 |
| X2 | 回滚动作逐条写进技术设计文档，照着执行即可 | P0 |

## 五、验收标准

以下全部通过才算本期完成：

**采集侧**
- [ ] `horizon-wxmp-collector` 一条命令启动后持续运行，可 Ctrl+C 优雅退出
- [ ] 各公众号的抓取时间在 4-8 小时区间内随机错开，不集中在同一时刻
- [ ] 未登录时启动，进程打印提示后继续运行（不崩溃），可登录后再生效
- [ ] 单号失败不影响其他号继续抓
- [ ] 同一 URL 的文章重复抓取不产生中间表重复行
- [ ] 已被两条管道消费且发布超 60 天的文章被自动清理；未消费的过期文章保留不删

**消费侧**
- [ ] `horizon --date <某日>` 跑出与旧行为等价的日报，微信文章正常进入 items 表
- [ ] 同一天重复跑 `horizon`,微信文章不重复处理
- [ ] 中间表为空时跑 `horizon`,微信内容不丢（自动降级实时抓取）
- [ ] `horizon-reports` 跑出微信报告,进入 reports 表
- [ ] 关闭 `use_collector` / `use_store` 后,行为完全回到现状(回归测试全绿)

**可迁移性**
- [ ] 在一台干净的机器上按"最小步骤"部署,采集 + 日报 + 报告全链路跑通

## 六、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 微信转发服务（weread.111965.xyz）本身不稳或倒闭 | 采集进程抓不到数据 | 中间表为空时日报/报告自动降级实时抓取；转发服务地址可配置，可换服务商 |
| 登录态过期（微信 token 30 天提醒） | 采集进程停摆 | fail-open:进程持续运行并提示重登;`horizon-wxmp login` 重新扫码即可 |
| 分散抓取后日报内容"新鲜度"下降几小时 | 日报可能比旧的集中抓取晚几小时收录某篇文章 | 属可接受权衡;若用户不接受,后续可加"日报运行前补抓一次"选项 |
| 实现复杂、实测效果不如预期 | 白费工作量 | 可回滚性设计:新代码整体隔离,关闭开关即回到旧行为,删除成本低 |
| 与采集进程并发访问 SQLite | 写锁等待 | 沿用现有架构(API 与管道本就多进程共库),采集写入是低频少量,冲突概率低 |

## 七、回滚策略

**判定标准**：上线后观察 2-4 周,若微信内容量/稳定性不升反降,或转发服务与采集进程的维护成本超出收益,则回滚。

**回滚三步**(细节见技术设计文档"回滚清单"):

1. **关开关**:`data/config.py` 把 `sources.wxmp.use_collector` 设为 `False`(报告侧 `use_store` 同理),新闻/报告管道立即回到旧的实时抓取行为。
2. **停进程**:停掉 `horizon-wxmp-collector` 常驻进程。
3. **删代码**(可选,彻底回滚):删除 `src/wxmp_collector/` 目录 + `pyproject.toml` 里一条脚本入口 + 对应测试;drop 中间表。现有 `items` / `reports` 数据与全部历史行为不受影响。
