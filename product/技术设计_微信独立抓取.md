## 一、架构与数据流

```
微信转发服务 weread.111965.xyz
        │  (src/we_read 纯 HTTP,双节流:转发服务 20s±5 / 正文页 2s±2)
        ▼
horizon-wxmp-collector 常驻 daemon ──每号随机 4-8h 间隔──┐
        │ upsert 中间表 wxmp_articles                    │
        ▼                                               │
   [wxmp_articles 中间表] ◄──────────────────────────────┘
        │ 读(时间窗口 + 消费标记)                          │
   ┌────┴─────────────┐
   ▼                  ▼
新闻管道(horizon)    报告管道(horizon-reports)
→ items 表           → reports 表(PDF 由 WxmpBrowserResolver 补齐)
```

设计原则:

1. **一次抓取、两处消费**:daemon 抓到的文章只进中间表;新闻/报告管道各自按需读取,不再重复调 `src/we_read`。
2. **消费标记互不干扰**:新闻按日报 `run_date` 粒度标记,报告按时间戳粒度标记,两列独立。
3. **fail-open**:中间表为空(新机器首启 / CI)时,两条管道自动降级为实时抓取,行为与现状等价。
4. **可回滚**:新代码整体隔离在独立包 + 新表,关闭开关即回旧行为(见第六节回滚清单)。

### 2.5 数据保留与自动清理

**问题**:中间表若只增不清,按 31 号 × ~4 篇/天、每篇 50-200KB 估算,一年累积约 4-6 GB。而消费端窗口最宽 7 天(报告),新闻仅 1 天——超出窗口的文章已是"死数据",应清理。

**策略(数据安全优先,只清已消费数据)**:

1. **只清理"已被两条管道都消费过、且发布超过保留期"的行**:`prune_wxmp_articles` 的 DELETE 带 `consumed_news_run_date IS NOT NULL AND consumed_reports_at IS NOT NULL` 条件。**未消费的过期行一律保留**——万一某条管道长期没跑,待处理数据不能被误删。
2. **保留期默认 60 天**(`--retention-days`,可配置)。60 天 ≫ 最大消费窗口(报告 `--max-age` 可调大、新闻 `--hours` 可调大),留足余量;停机恢复也在 60 天内。
3. **触发时机**:daemon 启动时执行一次 + 调度循环内每轮检查(间隔超 retention 一半时触发),`once` 模式结束时也执行;另提供手动 `prune` 子命令。
4. **正常规模**:中间表稳定在 ~60 天 × 每日新增量(约 60 × 120 篇 ≈ 7200 行,含正文约 1 GB 内),不再无限增长。

> 不清理"已消费"标记本身:即使行被删,`consumed_*` 标记只存在于被删行内,无外部残留。

## 三、Collector 常驻进程

### 3.0 时间窗口模型(重要)

`we_read.list_articles(page=1)`(client.py:210-230)请求转发服务 `/api/v2/platform/mps/{mp_id}/articles`,**返回该公众号当前可获取的文章列表**——转发服务单页返回(通常为最近数日到数周的几十篇),**不按时间过滤、没有游标/增量机制**。`publish_time` 只是每条文章带的一个字段,列表本身不是"某时间窗内"的查询。

据此,本方案的时间窗口职责划分:

| 环节 | 时间窗口 | 说明 |
|---|---|---|
| **采集端(collector)** | **无窗口(增量累积)** | 每次 `list_articles(page=1)` 拿"当前列表",与中间表已有 URL 去重,把**新增**文章入库。中间表 = 各号近期文章的累积快照。可选 `--max-age-days` 限制入库文章的最早发布时间(默认不限) |
| **新闻消费端** | `published_at >= 昨日 00:00 UTC` | `WxmpStoredScraper` 用 `since.timestamp()` 从中间表筛 |
| **报告消费端** | `published_at >= 今天 − max_age_days(默认 7 天)` | store 分支用 `cutoff` 从中间表筛 |

**没有显式窗口的后果(诚实说明)**:

1. **首次部署**:会把每个号"当前列表"里的文章全部灌入(可能含较早发布的),但消费端按窗口筛,老文章不进日报/报告,中间表是缓存、多存无害。
2. **增量**:每次只新增该号最新的、中间表里没有的文章。
3. **潜在漏抓**:若某号在两次抓取间隔内发文数超过转发服务单页返回上限(例如上限 20 篇而该号 8h 内发了 25 篇),被挤出列表的最老几篇会漏抓。公众号通常日发 < 10 篇,4-8h 间隔 + 每日 3-6 轮,实际风险很低;若个别大号担心,可调小 `--interval-max` 或对特定号更频繁抓取。

### 3.3 调度循环 `src/wxmp_collector/daemon.py`

**随机与并发模型**(回答"多号会不会同时抓"):

- **单线程串行,绝不并发**:daemon 是单 asyncio 循环,`for f in due:` 逐个 `await sync_feed`,同一时刻**只有一个公众号在抓**,不存在多个号并发抓取。
- **随机体现在两层**:
  1. 每个号的抓取间隔是 `[4h, 8h]` 均匀随机(`random.randint`),每次抓完**重新掷一次**,间隔不固定;
  2. 每个号的"下次抓取时刻" = 上次抓完时刻 + 该随机间隔,因此**不同号的到期时刻天然错开**,同号自身每天 3-6 轮也落在不同钟点。
- **同轮到点的号之间再打散**:若同一轮检查有多个号同时到期,处理完一个号后插入 `asyncio.sleep(random.uniform(30, 180))`(可中断、查 stop),把"同时到期"的号再分散到 1-3 分钟内,避免连续紧抓。
- **最后一道保险是 api_pacer**:`WeReadClient` 内置的转发服务节流 `api_pacer`(20s±5)是**全局共享**的——即使两个号几秒内先后被处理,后一个的 `list_articles` 也会自动等到距上一次转发服务请求 ≥20s 才发出。即使完全同秒到期,转发服务层面也保证 ≥20s 间隔。
- **首启避免全号立即抓**:每个号首次 `next_run_at = now + random(4h, 8h)`,启动瞬间 31 个号全部静默,各自在 4-8h 后的随机时刻开始第一轮。

```python
async def run_daemon(config, *, interval=(4*3600, 8*3600), max_age_days=None,
                     retention_days=60, once=False) -> None:
    wxmp = config.sources.wxmp
    feeds = [f for f in wxmp.feeds if f.enabled and f.weread_mp_id]
    state, db = WeReadSyncState(), HorizonDB()
    client = build_client_from_wxmp_config(wxmp)          # __init__.py:63
    if not client.store.is_present():                     # token_store.py:44
        logger.warning("微信读书未登录，先运行 `horizon-wxmp login` 扫码。")  # fail-open

    for f in feeds:                                       # 首启每号随机初始计划时间(非立即)
        if state.feed_next_run(f.weread_mp_id) is None:
            state.record_feed_schedule(f.weread_mp_id, int(time.time()) + random.randint(*interval))

    stop = asyncio.Event()
    loop.add_signal_handler(SIGINT, stop.set); loop.add_signal_handler(SIGTERM, stop.set)
    _prune_if_due(db, retention_days)                     # 启动时清理一次
    last_prune = time.time()
    try:
        while not stop.is_set():
            now = time.time()
            due = [f for f in feeds if state.feed_next_run(f.weread_mp_id) <= now]
            for i, f in enumerate(due):
                try:
                    await sync_feed(client, f, db, wxmp, max_age_days)
                    state.record_feed_success(f.weread_mp_id)
                except WeReadAuthError:
                    logger.warning("登录失效，跳过 %s；运行 `horizon-wxmp login` 重新扫码。", f.name)
                except WeReadError as exc:
                    logger.warning("抓取 %s 失败(fail-open): %s", f.name, exc)
                finally:
                    state.record_feed_schedule(f.weread_mp_id, int(time.time()) + random.randint(*interval))
                if i < len(due) - 1:                      # 同轮到点的号之间再随机打散 30-180s
                    await _sleep_interruptible(random.uniform(30, 180), stop)
            if time.time() - last_prune > retention_days * 3600 / 2:
                _prune_if_due(db, retention_days)
                last_prune = time.time()
            if once:
                break
            await wait_until_next_due(state, feeds, stop) # 最近 next_run_at,30s 轮询查 stop
    finally:
        await client.aclose()                             # client.py:102

def _prune_if_due(db, retention_days) -> None:
    cutoff = datetime.now(timezone.utc) - timedelta(days=retention_days)
    n = db.prune_wxmp_articles(_dt_iso(cutoff))
    if n:
        logger.info("清理 %d 条已消费且过期的中间表文章(保留 %d 天)", n, retention_days)
```

`wait_until_next_due` / `_sleep_interruptible`:`asyncio.wait({sleep(task), stop.wait()})`,既等最近 `next_run_at`(30s 轮询),又随时响应 SIGINT/SIGTERM;所有 feed 都过了 `next_run_at` 时立即返回(避免空转)。

### 3.4 `sync_feed` 单号抓取

复用 `with_empty_retry`(we_read/__init__.py:28)、清洗函数 `fix_wechat_images` / `sanitize_wxmp_display_html` / `_html_to_text`(src/scrapers/wxmp.py,直接 import):

```python
async def sync_feed(client, feed, db, wxmp, max_age_days=None) -> int:
    arts = await with_empty_retry(
        lambda: client.list_articles(feed.weread_mp_id, page=1),
        waits=wxmp.weread.empty_retry_waits, max_empties=wxmp.weread.empty_max_retries,
        log=logger, ctx=f"公众号 {feed.name}")
    existing = db.get_wxmp_article_urls(feed.weread_mp_id)   # 命中→不重复抓正文
    rows = []
    for art in arts:
        if not art.url or art.url in existing:
            continue
        if max_age_days is not None:                          # 可选窗口:过滤老文章
            published_dt = datetime.fromtimestamp(float(art.publish_time), tz=timezone.utc)
            if published_dt < datetime.now(timezone.utc) - timedelta(days=max_age_days):
                continue
        raw = ""
        if wxmp.gather_content:
            try:
                raw = await client.fetch_article_html(art.url)   # article_pacer 2s±2
            except WeReadError as exc:
                logger.warning("单篇正文失败留空: %s", exc)        # 不拖垮整号
        raw_html = fix_wechat_images(raw)
        rows.append(WxmpArticle(
            id=f"wechat:{feed.weread_mp_id}:{art.id}",           # 与 base.py:36 格式一致
            feed_name=feed.name, weread_mp_id=feed.weread_mp_id, native_id=art.id,
            title=art.title, url=art.url, cover_image=art.pic_url,
            published_at=datetime.fromtimestamp(float(art.publish_time), tz=timezone.utc),
            raw_html=raw_html or None,
            display_html=sanitize_wxmp_display_html(raw_html) or None,
            content_text=_html_to_text(raw_html) or None,
            content_hash=sha1(art.url),
            fetched_at=_now_iso(), last_synced_at=_now_iso()))
    return db.upsert_wxmp_articles(rows)
```

节流无需新代码:daemon 共享单一 `WeReadClient`,其内置 `api_pacer`(20s±5)/`article_pacer`(2s±2)即全局节流。`list_articles` 空响应用 `with_empty_retry` 兜频控。

           ...

## 九、风险与注意

- **崩溃重跑同日期**:新闻标记在首次落库成功后写入,崩溃落在标记前则重跑重新处理(重复但不丢);`reset-news` 手动恢复。
- **CI(无 collector 数据)**:stored scraper 空窗口自动 fallback 实时,对 GitHub Actions 透明。
- **`fetch_all_sources` / `fetch_all_reports` 签名变更**:新增带默认值关键字参数,MCP 等既有调用不受影响。
- **正文抓取节流**:daemon 与新闻/报告共用 `WeReadClient` 内置双通道,不新增节流代码。
- **SQLite 并发**:daemon 低频少量写,沿用现有多进程共库架构,冲突概率低。
